# Sofia SRE & Security

Три правила, определяющие вердикты этого контура:

```
NO DATA != GREEN
HEALER RECOVERY != STABLE SYSTEM
BACKUP != VERIFIED BACKUP WITHOUT RESTORE TEST
```

Отсутствие алертов не является доказательством здоровья: это либо здоровье, либо неработающий мониторинг. До выяснения — `NOT_MEASURED`, не `PASS`.

## GPU GOVERNANCE

**`ONE HEAVY GPU OWNER`** — одновременно тяжёлую GPU-задачу выполняет ровно один владелец.

Перед запуском проверить: `nvidia-smi`, температуру, свободный VRAM, отсутствие активного `gpu_render`, состояние ComfyUI и отсутствие конкурирующего процесса.

`CUDA OOM` — не повод немедленно перезапускать: сначала установить, кто реально держал память и почему профиль не соответствовал источнику.

**Gaming Pause** — игровой режим владельца приостанавливает тяжёлые задачи. Не обходить и не «дожимать» задачу во время паузы.

## LOCKS / SCHEDULER / ORCHESTRATOR / PUBLISHER

**`ONE ORCHESTRATOR`**, **`ONE PUBLISHER`.** Обнаруженный второй экземпляр — инцидент `P0`, а не особенность конфигурации.

Проверять locks вместе с реальными владельцами процессов: осиротевший lock и живой владелец лечатся по-разному. Zombie publisher — блокирующий сигнал для любой публикации.

Windows Task Scheduler, службы, автозапуск и elevated-скрипты изменяются только по отдельной явной команде владельца. Диагностировать и докладывать можно всегда.

## DB / QUEUE

Проверять integrity БД, согласованность очереди с фактическими артефактами, отсутствие зависших и дублирующихся задач. Расхождение между очередью и файловой системой разбирать до запуска нового цикла.

## SECRETS / DPAPI

Секреты хранятся штатным механизмом (DPAPI). Не копировать значения в логи, отчёты, промпты или коммиты. Не репурпозить credentials между контурами. Не использовать private API.

В отчётах указывать расположение секрета и статус, а не значение.

## MONITORING / SELF-HEALING

Healer восстанавливает работоспособность, но не отменяет разбор. Каждое срабатывание healer — запись об инциденте с root cause, иначе система выглядит зелёной при хронической деградации.

Повторяющееся восстановление одного и того же компонента — `WARN` минимум, независимо от текущего состояния.

## BACKUP / RESTORE

Бэкап без успешного restore-теста не считается бэкапом. Фиксировать: дату бэкапа, дату последнего проверенного восстановления, охват и время восстановления.

Никогда не удалять файлы и журналы. Не обходить `.claude\hooks\block_delete.py`. Для замены критичного файла — backup/rollback по штатной процедуре и атомарная запись: temp → parse/validate → atomic replace.

## HOST STABILITY / INCIDENTS

`Kernel-Power`, `WHEA` и внезапные перезагрузки разбирать как аппаратные или драйверные сигналы, а не как сбой pipeline. Сопоставлять по времени с GPU-нагрузкой, температурой и последним прогоном.

Разбор инцидента: симптом → окно времени → живые логи → затронутый контур → root cause → минимальное обратимое исправление → проверка → запись в Failure Memory.

При неоднозначности, конфликте состояний или отсутствии доказательств сохранять fail-closed позицию.
