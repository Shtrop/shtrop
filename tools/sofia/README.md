# Sofia AI Studio — сбор доказательств по инцидентам

`Collect-SofiaIncident.ps1` — **read-only** сборщик доказательств для алертов
`HOST_REBOOTED` и `JOB_STUCK` от Sofia Studio Telegram Control.

Скрипт не перезапускает сервисы, не удаляет файлы и локи, не снимает флаги публикации,
не меняет Task Scheduler и не инициирует reboot. Он только читает состояние
и складывает артефакты в отдельную папку отчёта.

## Запуск

Запускать **от администратора** и **до перезапуска зависшего процесса** — рестарт
уничтожает стек и делает причину `JOB_STUCK` недоказуемой.

```powershell
powershell -ExecutionPolicy Bypass -File .\Collect-SofiaIncident.ps1 -StuckPid 26520
```

Если `py-spy` ещё не установлен (без него стек зависания не снимется):

```powershell
pip install py-spy
```

Параметры:

| Параметр | По умолчанию | Назначение |
|---|---|---|
| `-StuckPid` | автопоиск | PID из алерта `JOB_STUCK`. Без него процесс ищется по командной строке и по слушающему порту |
| `-SofiaRoot` | `D:\AI_CONTENT\Sofia` | Корень студии |
| `-OutDir` | `<SofiaRoot>\reports\incident_<timestamp>` | Куда писать отчёт |
| `-CrashDays` | `7` | Глубина разбора журнала событий |
| `-DashboardPort` | `5681` | Порт dashboard для проверки API |
| `-AllowPySpyInstall` | выкл. | Разрешить `pip install py-spy`. Без ключа скрипт строго read-only |

## Как читать результат

**HOST_REBOOTED — root cause падений:**

- `WHEA` = `FAIL` → отказ железа (RAM/CPU/PCIe/питание). Дальше: MemTest86, проверка PSU.
- `BugCheck 1001` = `FAIL` + минидампы → драйвер. Дальше: `!analyze -v` в WinDbg, чаще всего GPU-драйвер.
- Только Kernel-Power 41, без WHEA и без дампов → обрыв питания, PSU или зависание. Дальше: PSU, розетка/UPS, температуры.
- `Корреляция падений с GPU-рендером` = `FAIL` → просадка PSU под нагрузкой.

**JOB_STUCK — почему завис dashboard:**

- Нижний фрейм в `11_pyspy_dump.txt` и есть причина:
  - `recv` / `read` / `connect` → сетевой вызов без timeout;
  - `acquire` / `wait` / `join` → deadlock или ожидание лока;
  - нет потока heartbeat → watchdog-поток умер: сервис жив, но не отчитывается;
  - стек в файловых операциях + ошибки диска → подвисший I/O.
- `Стек за 5 секунд` = `FAIL` → процесс реально заблокирован, а не просто молчит.
- `Stale-локи после ребута` = `FAIL` → лок от мёртвого PID держит pipeline. Это связывает оба алерта в одну причину.

## Границы автономности

Скрипт намеренно НЕ делает и оставляет владельцу:

- снятие любых локов и флагов (NO-DELETE — только показывает);
- перезапуск dashboard (только **после** снятия стека);
- MemTest86 / `mdsched`, изменения автозапуска и Task Scheduler — влекут reboot;
- снятие `FROZEN` и публикацию — запрещены, пока `host_state = DEGRADED`.

## Проверка

Скрипт разобран парсером PowerShell 7.4.6 без ошибок и прогнан end-to-end:
на подготовленном дереве студии подтверждены детект stale-лока от мёртвого PID,

корректно классифицировал его как неподвижный.
