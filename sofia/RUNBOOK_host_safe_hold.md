# Runbook: GOVERNOR [CRITICAL] host_unstable_safe_hold

Инцидент: governor зафиксировал критическую частоту событий Windows **Kernel-Power 41**,
выставил `control_flags\HOST_SAFE_HOLD.flag` и остановил конвейер.

Это **штатное fail-closed поведение**, а не сбой пайплайна. Флаг защищает от потери
артефактов и от обрыва GPU-рендера посреди работы. Снятие флага без закрытия root cause
вернёт систему под тот же ресет.

---

## 0. Что нельзя делать до закрытия root cause

| Запрещено | Почему |
|---|---|
| Удалять `HOST_SAFE_HOLD.flag` | Снимает защиту, конвейер снова пойдёт под ресет |
| Чистить `.lock` вручную | После жёсткого ресета локи stale; чистить только штатным механизмом |
| Перезапускать сервисы «на всякий случай» | Маскирует симптом, ломает доказательную базу |
| Снимать `FROZEN`, убирать `PUBLISHING_DISABLED.flag` | Публикация fail-closed, только решением владельца |
| Reboot, правки Task Scheduler, elevated-скрипты | Только решением владельца, вручную |
| Удалять логи и инциденты | NO-DELETE |

## 1. Собрать доказательства (read-only, 1 команда)

На машине студии, PowerShell **от имени администратора** (нужно только для чтения журнала System):

```powershell
powershell -ExecutionPolicy Bypass -File .\diagnose_host_safe_hold.ps1
```

Параметры при необходимости:

```powershell
# другое окно анализа и другой корень
.\diagnose_host_safe_hold.ps1 -Days 14 -SofiaRoot 'D:\AI_CONTENT\Sofia'
```

Скрипт ничего не изменяет в дереве студии. Результат:

- `%TEMP%\sofia_safehold_<timestamp>\safehold_report.json` — машиночитаемые доказательства;
- `console.log` — полный транскрипт.

Сразу после сбора получить диагноз, не отправляя отчёт никуда:

```powershell
.\analyze_safehold_report.ps1
```

Анализатор сам находит свежий отчёт, взвешивает улики по таблицам ниже,
ранжирует гипотезы root cause и печатает одну минимальную команду следующего шага.
Отчёт можно прислать и мне — но решение он выдаёт без этого.

## 2. Дерево решений по результату

### Секция 1 — события Kernel-Power 41

| Наблюдение | Классификация | Вывод |
|---|---|---|
| 0 событий за окно | `PASS` | Причина hold не в питании — смотреть incident-файл governor |
| 1–2 события | `WARN` | Наблюдать, hold пока держать |
| ≥3 события | `FAIL` | Хост нестабилен, hold обязателен до устранения |
| Есть BugCheck **1001** | `FAIL`, но это удача | Есть код остановки и минидамп → root cause определяется точно: `.\analyze_minidump.ps1` |
| Дампов меньше, чем событий 41 | `FAIL`, **две причины** | События без дампа — потеря питания; события с дампом — крах драйвера. Закрывать оба направления, не одно |
| Событий 41 нет BSOD-дампов | — | Классика внезапной потери питания: ОС не успела записать дамп |

Регулярные интервалы между событиями (поле `gaps_hours`) — признак воспроизводимого
триггера по расписанию: сверить с временем запуска Reel/render-задач.

### Коды остановки

`analyze_minidump.ps1` печатает код и класс причины. Ориентиры:

| Класс | Типичные коды | Куда копать |
|---|---|---|
| `gpu` | `0x116`, `0x117`, `0x119`, `0x113`, `0x141`, `0xEA` | Драйвер NVIDIA начисто через DDU, снять OC, ограничить power limit, температура |
| `hardware` | `0x124` WHEA, `0x101`, `0x9F`, `0x14C` | Питание/PSU, ИБП, разгон, VRM — не драйвер |
| `memory` | `0x154`, `0x1A`, `0x50`, `0x12B`, `0x109`, `0x19`, `0x4E`, `0x13A` | `.\check_memory_storage.ps1`, отключить XMP/EXPO, MemTest86 ≥ 4 прохода |
| `storage` | `0x133`, `0xF4` | Прошивка NVMe, драйвер контроллера, SMART системного диска |

### 0x154 UNEXPECTED_STORE_EXCEPTION

Падение менеджера сжатой памяти. Три типовые причины, в порядке проверки:

1. **Нестабильный XMP/EXPO** — отключить профиль в BIOS. Бесплатно и обратимо.
2. **Сбойная планка RAM** — MemTest86 с флешки, минимум 4 прохода. Проверка из-под Windows слабее.
3. **Системный диск** — на нём живут файл подкачки и store: SMART, прошивка NVMe, события `disk`/`Ntfs` 7/51/129/153.

Доказательства по всем трём собирает `.\check_memory_storage.ps1` (только чтение).
Повтор одного и того же кода в нескольких дампах — признак постоянного дефекта, а не совпадения.

### Секция 4 — корреляция событий 41 с GPU-нагрузкой

| Наблюдение | Гипотеза (`AI ANALYSIS`, не факт) | Проверка |
|---|---|---|
| Все события 41 попали в окна рендера ±20 мин | Транзиентные пики RTX 5090 роняют линию 12V PSU | Ограничить power limit, повторить нагрузку |
| Часть событий вне окон рендера | Смешанная причина: сеть/PSU + нагрузка | Добавить ИБП, затем повторить наблюдение |
| События вне окон рендера | Питание сети, PSU, драйверы чипсета, RAM | GPU-гипотезу отбросить, смотреть питание и память |
| `Thermal`/`HW Power Brake` активны в throttle reasons | Охлаждение или питание | Почистить радиаторы, проверить кривую вентиляторов |

## 3. Минимальный обратимый fix (только после подтверждения GPU-гипотезы)

Порядок — от самого дешёвого и обратимого:

1. **Ограничить power limit GPU** (обратимо, без вскрытия корпуса):
   ```powershell
   .\apply_safehold_fix.ps1 -Action PowerLimit -Percent 80            # dry-run, ничего не меняет
   .\apply_safehold_fix.ps1 -Action PowerLimit -Percent 80 -Confirm   # применить
   ```
   Исходный лимит сохраняется в файл отката автоматически.
   Откат: `.\apply_safehold_fix.ps1 -Action Rollback -Confirm`.
   Скрипт не трогает `HOST_SAFE_HOLD.flag`, publishing state, сервисы и планировщик.

2. **Запретить параллельные GPU-задачи** через `gpu_resource_scheduler` — один
   `gpu_render` в моменте. Изменение конфига: temp → validate → atomic replace, с backup.

3. **Сбросить любой OC-профиль** (MSI Afterburner и аналоги) до стоковых значений.

4. **Контрольный прогон**: штатный runner в `local-only` / `no-publish` / `dry-run`,
   фото-ветка (не Reel — короче и дешевле по GPU). Критерий успеха: прогон завершён,
   новых событий 41 нет.

5. Если события 41 повторяются на сниженном power limit — проблема вне GPU:
   PSU (мощность/возраст/просадка), сеть, ИБП. Это железо, решение владельца.

**Критерий выхода из hold:** N суток непрерывной работы под штатной нагрузкой без новых
событий 41, подтверждённые повторным запуском этого скрипта. N задаёт владелец; разумный
минимум — 48 ч с минимум одним полным production-циклом.

Окно наблюдения собирается автоматически:

```powershell
.\watch_host_stability.ps1 -Hours 48
```

Скрипт снимает телеметрию GPU, ловит новые события 41/6008/1001 и в конце выдаёт
`PASS`/`FAIL`/`NOT_MEASURED` с CSV и итоговым JSON. Ничего не изменяет.

---

## 4. Снятие hold и возврат в работу

Только после выполнения п.3 и явного решения владельца:

1. `watch_host_stability.ps1 -Hours 48` → вердикт `PASS`, затем повторный
   `diagnose_host_safe_hold.ps1` → в секции 1 должно быть 0 новых событий 41.
2. Штатный `REBOOT_PRECHECK.ps1` → требовать `PASS`.
3. Физический reboot выполняет владелец.
4. Штатный `REBOOT_POSTCHECK.ps1` → требовать `PASS`.
5. Снять hold штатной процедурой governor (не `del` по файлу).
6. Контрольный `--no-publish` прогон.
7. Publishing state **не трогать**: возврат из `FROZEN` — отдельное решение владельца
   после закрытия release blockers, и к этому инциденту отношения не имеет.

## 5. Что записать в инцидент

- timestamps всех событий 41 и их частота;
- время выставления `HOST_SAFE_HOLD.flag` и сработавший порог governor;
- корреляция с GPU-нагрузкой (совпало / не совпало);
- применённый fix, исходные значения для отката, хэши изменённых конфигов;
- результат контрольного прогона и окно наблюдения без событий 41.

Исторические `FAIL` не переписывать и не удалять.
