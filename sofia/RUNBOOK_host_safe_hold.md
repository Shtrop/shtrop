# Runbook: GOVERNOR [CRITICAL] host_unstable_safe_hold

Инцидент: governor зафиксировал критическую частоту событий Windows **Kernel-Power 41**,
выставил `control_flags\HOST_SAFE_HOLD.flag` и остановил конвейер.

Это **штатное fail-closed поведение**, а не сбой пайплайна. Флаг защищает от потери
артефактов и от обрыва GPU-рендера посреди работы. Снятие флага без закрытия root cause
вернёт систему под тот же ресет.

---

## 0. Что нельзя делать до закрытия root cause

| Запрещено | Почему |
|---|---|
| Удалять `HOST_SAFE_HOLD.flag` | Снимает защиту, конвейер снова пойдёт под ресет |
| Чистить `.lock` вручную | После жёсткого ресета локи stale; чистить только штатным механизмом |
| Перезапускать сервисы «на всякий случай» | Маскирует симптом, ломает доказательную базу |
| Снимать `FROZEN`, убирать `PUBLISHING_DISABLED.flag` | Публикация fail-closed, только решением владельца |
| Reboot, правки Task Scheduler, elevated-скрипты | Только решением владельца, вручную |
| Удалять логи и инциденты | NO-DELETE |

## 1. Собрать доказательства (read-only, 1 команда)

На машине студии, PowerShell **от имени администратора** (нужно только для чтения журнала System):

```powershell
powershell -ExecutionPolicy Bypass -File .\diagnose_host_safe_hold.ps1
```

Параметры при необходимости:

```powershell
# другое окно анализа и другой корень
.\diagnose_host_safe_hold.ps1 -Days 14 -SofiaRoot 'D:\AI_CONTENT\Sofia'
```

Скрипт ничего не изменяет в дереве студии. Результат:

- `%TEMP%\sofia_safehold_<timestamp>\safehold_report.json` — машиночитаемые доказательства;
- `console.log` — полный транскрипт.

Сразу после сбора получить диагноз, не отправляя отчёт никуда:

```powershell
.\analyze_safehold_report.ps1
```

Анализатор сам находит свежий отчёт, взвешивает улики по таблицам ниже,
ранжирует гипотезы root cause и печатает одну минимальную команду следующего шага.
Отчёт можно прислать и мне — но решение он выдаёт без этого.

## 2. Дерево решений по результату

### Секция 1 — события Kernel-Power 41

| Наблюдение | Классификация | Вывод |
|---|---|---|
| 0 событий за окно | `PASS` | Причина hold не в питании — смотреть incident-файл governor |
| 1–2 события | `WARN` | Наблюдать, hold пока держать |
| ≥3 события | `FAIL` | Хост нестабилен, hold обязателен до устранения |
| Есть BugCheck **1001** | `FAIL`, но это удача | Есть код остановки и минидамп → root cause определяется точно: `.\analyze_minidump.ps1` |
| Дампов меньше, чем событий 41 | `FAIL`, **две причины** | События без дампа — потеря питания; события с дампом — крах драйвера. Закрывать оба направления, не одно |
| Событий 41 нет BSOD-дампов | — | Классика внезапной потери питания: ОС не успела записать дамп |

Регулярные интервалы между событиями (поле `gaps_hours`) — признак воспроизводимого
триггера по расписанию: сверить с временем запуска Reel/render-задач.

### Коды остановки

`analyze_minidump.ps1` печатает код и класс причины. Ориентиры:

| Класс | Типичные коды | Куда копать |
|---|---|---|
| `gpu` | `0x116`, `0x117`, `0x119`, `0x113`, `0x141`, `0xEA` | Драйвер NVIDIA начисто через DDU, снять OC, ограничить power limit, температура |
| `hardware` | `0x124` WHEA, `0x101`, `0x9F`, `0x14C` | Питание/PSU, ИБП, разгон, VRM — не драйвер |
| `memory` | `0x154`, `0x1A`, `0x50`, `0x12B`, `0x109`, `0x19`, `0x4E`, `0x13A` | `.\check_memory_storage.ps1`, отключить XMP/EXPO, MemTest86 ≥ 4 прохода |
| `storage` | `0x133`, `0xF4` | Прошивка NVMe, драйвер контроллера, SMART системного диска |

### 0x154 UNEXPECTED_STORE_EXCEPTION

Падение менеджера сжатой памяти. Три типовые причины, в порядке проверки:

1. **Нестабильный XMP/EXPO** — отключить профиль в BIOS. Бесплатно и обратимо.
2. **Сбойная планка RAM** — MemTest86 с флешки, минимум 4 прохода. Проверка из-под Windows слабее.
3. **Системный диск** — на нём живут файл подкачки и store: SMART, прошивка NVMe, события `disk`/`Ntfs` 7/51/129/153.

Доказательства по всем трём собирает `.\check_memory_storage.ps1` (только чтение).
Повтор одного и того же кода в нескольких дампах — признак постоянного дефекта, а не совпадения.

### WHEA: компонент «память»

Событие WHEA-Logger с `Компонент: память` и непустым `PhysicalAddress` — это не гипотеза,
а зафиксированная платформой ошибка по конкретному адресу. В сочетании с `0x154` она
закрывает вопрос в пользу RAM.

Windows умеет исключать такие страницы из использования:

```powershell
.\apply_safehold_fix.ps1 -Action BadMemoryList              # dry-run: покажет адреса и PFN
.\apply_safehold_fix.ps1 -Action BadMemoryList -Confirm     # применить
```

Скрипт сам собирает адреса из событий WHEA, переводит их в номера страниц (`PFN = адрес / 4096`),
дописывает в `bcdedit /set {badmemory} badmemorylist`, сохраняя прежний список для отката.
Адреса из отчёта MemTest86 добавляются параметром `-Address 0x...`.

**Адрес не указывает на планку.** При чередовании (interleaving) соседние физические адреса
раскладываются по всем модулям, поэтому по адресу нельзя сказать, какой слот виноват: адреса
одного дефектного модуля размазаны по всему диапазону. Слот определяет только MemTest86
(он сопоставляет отказы со SMBIOS) или перестановка планок.

Границы честно: исключается **только та страница, по которой ошибка уже произошла**. Дефект
планки никуда не девается, и соседние ячейки могут отказать следом. Это способ дожить до
замены памяти, а не замена ремонта. Полный список плохих адресов даёт MemTest86.

**Обратимое смягчение, пока причина ищется.** Падение происходит внутри менеджера
сжатой памяти, поэтому его можно убрать из схемы:

```powershell
.\apply_safehold_fix.ps1 -Action MemoryCompression            # dry-run
.\apply_safehold_fix.ps1 -Action MemoryCompression -Confirm   # применить
```

Вступает в силу после перезагрузки, откат — `-Action Rollback -Confirm`. Это **не лечит**
сбойную планку или прошивку: оно снимает конкретный путь отказа. Смысл имеет там, где
сжатие ничего не даёт — много RAM и почти не используемая подкачка. Если после этого
`0x154` исчезает, а другие коды появляются, дефект никуда не делся и ищется дальше.

### Секция 4 — корреляция событий 41 с GPU-нагрузкой

| Наблюдение | Гипотеза (`AI ANALYSIS`, не факт) | Проверка |
|---|---|---|
| Все события 41 попали в окна рендера ±20 мин | Транзиентные пики RTX 5090 роняют линию 12V PSU | Ограничить power limit, повторить нагрузку |
| Часть событий вне окон рендера | Смешанная причина: сеть/PSU + нагрузка | Добавить ИБП, затем повторить наблюдение |
| События вне окон рендера | Питание сети, PSU, драйверы чипсета, RAM | GPU-гипотезу отбросить, смотреть питание и память |
| `Thermal`/`HW Power Brake` активны в throttle reasons | Охлаждение или питание | Почистить радиаторы, проверить кривую вентиляторов |

### Владельцы GPU: правило ONE HEAVY GPU OWNER

Отчёт содержит секцию `gpu_owners` и вывод `GPU owners`. «На GPU есть задачи» —
это не диагноз: штатный рендер и два ComfyUI, оставшихся от прошлых прогонов,
выглядят одинаково, а ведут себя по-разному.

| Вывод | Что значит | Что делать |
|---|---|---|
| `PASS`, тяжёлых владельцев 0 | карта простаивает — ожидаемо при hold | ничего |
| `PASS`, тяжёлый владелец 1 | норма вне hold | ничего |
| `WARN`, владелец 1 при активном hold | при hold рендеров быть не должно | найти, кто и чем запустил задачу; hold не снимать |
| `FAIL`, тяжёлых владельцев ≥ 2 | нарушено ONE HEAVY GPU OWNER | закрыть лишнего владельца штатно, до этого нагрузочные прогоны бессмысленны |
| `WARN`, не отнесённая VRAM | занятая память не сходится с суммой по процессам | освобождение после рендера не отработало: искать зависшие процессы и post-render cleanup |
| `FAIL`, владелец не установлен | занята половина карты и больше, а чья память — неизвестно | тяжёлый маршрут не запускать: память может не освободиться под задачу |

Разрыв между занятой памятью и суммой по процессам считается **всегда**, а не
только когда тяжёлых владельцев нет: питон на карте и 27 ГиБ ничьих — это
одновременно нормальный владелец и настоящая проблема.

**Про `[N/A]` в `used_memory`.** На Windows под WDDM `nvidia-smi` почти никогда
не отдаёт per-process VRAM — это устройство драйвера, а не сбой. Поэтому
`[N/A]` не считается нулём: память берётся из счётчиков производительности
Windows (набор с именами экземпляров `pid_<N>_luid_..._phys_<N>`; имя самого
набора локализовано, поэтому искать по нему нельзя). Если и счётчики не дались,
отчёт пишет `attribution: not_measured` — «не измерено», а не «памяти нет».

**Чему верить про свободную VRAM.** ComfyUI показывает свободную память своего
аллокатора torch, а не карты. Расхождение вида «ComfyUI: свободно 6 710 MiB» при
`nvidia-smi`: занято 30 803 MiB из 32 607 — это не противоречие в данных, а
признак того, что память держит кто-то вне ComfyUI. Решение принимать по карте.

Два тяжёлых владельца — это не «две задачи»: их транзиентные пики складываются
на одной линии 12V, поэтому анализатор усиливает гипотезу `gpu_transient`.
Осиротевшая VRAM опасна иначе: следующий рендер стартует на остатках памяти и
падает по OOM, а выглядит это как нестабильность модели.

## 3. Минимальный обратимый fix (только после подтверждения GPU-гипотезы)

Порядок — от самого дешёвого и обратимого:

1. **Ограничить power limit GPU** (обратимо, без вскрытия корпуса):
   ```powershell
   .\apply_safehold_fix.ps1 -Action PowerLimit -Percent 80            # dry-run, ничего не меняет
   .\apply_safehold_fix.ps1 -Action PowerLimit -Percent 80 -Confirm   # применить
   ```
   Исходный лимит сохраняется в файл отката автоматически.
   Откат: `.\apply_safehold_fix.ps1 -Action Rollback -Confirm`.
   Скрипт не трогает `HOST_SAFE_HOLD.flag`, publishing state и сервисы.

   **Сразу закрепить лимит**, иначе он исчезнет на первой же перезагрузке:

   ```powershell
   .\apply_safehold_fix.ps1 -Action PowerLimitPersist            # dry-run
   .\apply_safehold_fix.ps1 -Action PowerLimitPersist -Confirm   # закрепить
   ```

   `nvidia-smi -pl` живёт только до reboot, а п.4 этого runbook требует reboot
   перед выходом из hold. Без закрепления получается ловушка: окно наблюдения
   набирается на ограниченной карте, а производство возвращается на полной —
   то есть доказательства собраны не про тот режим, в который система выйдет.
   Закрепление — единственная строчка, в которой набор трогает планировщик:
   одна именованная задача на старт системы, снимается `Rollback`.

2. **Запретить параллельные GPU-задачи** через `gpu_resource_scheduler` — один
   `gpu_render` в моменте. Изменение конфига: temp → validate → atomic replace, с backup.

3. **Сбросить любой OC-профиль** (MSI Afterburner и аналоги) до стоковых значений.

4. **Контрольный прогон**: штатный runner в `local-only` / `no-publish` / `dry-run`,
   фото-ветка (не Reel — короче и дешевле по GPU). Критерий успеха: прогон завершён,
   новых событий 41 нет.

5. Если события 41 повторяются на сниженном power limit — проблема вне GPU:
   PSU (мощность/возраст/просадка), сеть, ИБП. Это железо, решение владельца.

**Критерий выхода из hold:** N суток непрерывной работы под штатной нагрузкой без новых
событий 41, подтверждённые повторным запуском этого скрипта. N задаёт владелец; разумный
минимум — 48 ч с минимум одним полным production-циклом.

Окно наблюдения собирается автоматически:

```powershell
.\watch_host_stability.ps1 -Hours 48
.\watch_host_stability.ps1 -Hours 48 -Resume   # продолжить то же окно после ресета
```

Решение принимается по полю **`hold_exit_ready`** в `stability_summary.json`,
а не по `verdict`. `verdict` отвечает только на вопрос «были ли крахи за окно»;
чистый час наблюдения тоже даёт `PASS`. Причины отказа перечислены в
`hold_exit_blockers`: недобранное наблюдение, пропуск внутри окна, нечитаемый
журнал System, откат power limit посреди окна, крахи или новые ошибки WHEA.

Порог применяется к фактически набранным часам наблюдения (`observed_hours`),
а не к календарному размаху окна (`window_span_hours`). Возобновить окно,
брошенное месяц назад, и получить «48 ч» за пять минут работы нельзя: разница
видна в `coverage_gap_hours` и отдельно блокирует выход.

Если хост ушёл в ресет посреди окна — продолжать через `-Resume`. Тогда события
ищутся от исходного старта окна, и событие 41 от самого этого ресета попадает в
отчёт. Новый запуск без `-Resume` начинает окно с текущего момента и такое
событие уже не увидит: окно будет выглядеть чистым, не будучи чистым.

Скрипт снимает телеметрию GPU, ловит новые события 41/6008/1001 **и новые ошибки WHEA**,
в конце выдаёт `PASS`/`FAIL`/`NOT_MEASURED` с CSV и итоговым JSON. Ничего не изменяет.

Новая ошибка WHEA обнуляет окно наравне с крахом: корректируемая ошибка появляется
раньше bug check, поэтому «крахов не было» при живом WHEA — это не чистое окно.
Новые адреса добавляются в список исключений тем же `-Action BadMemoryList -Confirm`.

## 4. Снятие hold и возврат в работу

Только после выполнения п.3 и явного решения владельца:

1. `watch_host_stability.ps1 -Hours 48` → вердикт `PASS`, затем повторный
   `diagnose_host_safe_hold.ps1` → в секции 1 должно быть 0 новых событий 41.
2. Штатный `REBOOT_PRECHECK.ps1` → требовать `PASS`.
3. Физический reboot выполняет владелец.
4. Штатный `REBOOT_POSTCHECK.ps1` → требовать `PASS`.
4a. **Проверить, что смягчение пережило перезагрузку:**
   ```powershell
   .\apply_safehold_fix.ps1 -Action Status
   ```
   В строке «Закрепление» должно быть `лимит закреплён`. Если там
   `НЕ закреплён`, а лимит применялся — после этой перезагрузки его уже нет,
   и окно наблюдения доказывало не тот режим, в который система сейчас вышла.
   Закрепить и набрать окно заново.
5. Снять hold штатной процедурой governor (не `del` по файлу).
6. Контрольный `--no-publish` прогон.
7. Publishing state **не трогать**: возврат из `FROZEN` — отдельное решение владельца
   после закрытия release blockers, и к этому инциденту отношения не имеет.

## 5. Что записать в инцидент

- timestamps всех событий 41 и их частота;
- время выставления `HOST_SAFE_HOLD.flag` и сработавший порог governor;
- корреляция с GPU-нагрузкой (совпало / не совпало);
- применённый fix, исходные значения для отката, хэши изменённых конфигов;
- закреплён ли power limit и что показал `Status` после перезагрузки;
- число тяжёлых владельцев GPU на момент сбора (`gpu_owners`);
- результат контрольного прогона и окно наблюдения без событий 41,
  вместе с `hold_exit_ready` и `hold_exit_blockers` из `stability_summary.json`.

Исторические `FAIL` не переписывать и не удалять.
